# ADR-0003. Уведомления и таймауты обрабатываются через очередь событий асинхронно

**Дата:** 2026-10-16
**Статус:** принято

## Контекст

После создания заказа система должна выполнить несколько независимых действий: отправить Push-уведомление клиенту, уведомить водителя, запустить таймер на 30 секунд для ожидания принятия заказа, записать событие в журнал. Эти действия не влияют на ответ клиенту — клиент должен увидеть стоимость и время подачи как можно быстрее. Если выполнять их синхронно, ответ задержится на секунды, а при сбое одного из них (например, Push-сервис недоступен) — весь заказ упадёт.

## Рассмотренные варианты

1. **Синхронная обработка внутри Backend API.** Все действия выполняются по очереди, ответ клиенту возвращается после их завершения. Просто, но медленно и хрупко: сбой Push-сервиса роняет заказ.
2. **Асинхронная обработка через очередь событий.** API публикует событие `RideCreated` в RabbitMQ и сразу возвращает ответ клиенту. Уведомления, таймауты и журналирование выполняет отдельный контейнер `worker`, который читает события из очереди.

## Решение

Вариант 2. Backend API публикует доменные события в очередь `bus` (RabbitMQ). Контейнер `worker` читает события и выполняет фоновые задачи: отправка Push-уведомлений, запуск таймаутов, запись в журнал, начисление штрафов.

## Последствия

**Плюсы:**
- Ответ клиенту возвращается быстро: API не ждёт завершения фоновых задач.
- Сбой Push-сервиса не роняет заказ: событие останется в очереди и будет обработано при восстановлении.
- `worker` масштабируется независимо: можно добавить поды при росте нагрузки.
- Появляется журнал событий: можно отследить, что и когда произошло.
- Легко добавить новых потребителей событий (например, аналитику) без изменения API.

**Минусы:**
- Появляется отдельный контейнер `worker` и очередь `bus` — усложняется развёртывание.
- Нужна обработка повторной доставки: событие может прийти дважды, `worker` должен быть идемпотентным.
- Нужен dead letter queue для событий, которые не удалось обработать.
- Клиент не может быть уверен, что уведомление доставлено, — только что оно поставлено в очередь.
- Отладка сложнее: нужно смотреть логи и API, и `worker`, и очереди.

**Что станет неверным, если решение пересмотреть:**
- C4 Container (исчезнут `bus` и `worker`).
- C4 Dynamic (шаги 10–12 с публикацией и доставкой события).
- Диаграмма последовательности `alt-flow.puml` (асинхронное сообщение `svc ->> bus : RideCreated`).
- Диаграмма развёртывания (уйдёт брокер сообщений и под `worker`).
