# Сравнение подходов C4-PlantUML и Structurizr DSL

## 1. Сколько раз название контейнера «Backend API» встречается в .puml-файлах и сколько — в workspace.dsl?

В `.puml`-файлах C4-PlantUML название «Backend API» встречается **три раза**:
- в `02-container.puml` — как `Container(api, "Backend API", "Kotlin / Spring Boot", ...)`;
- в `03-component.puml` — как `Container_Boundary(api, "Backend API")`;
- в `04-dynamic.puml` — как `Container(api, "Backend API", "Kotlin / Spring Boot", ...)`.

В `workspace.dsl` название «Backend API» встречается **один раз** — в объявлении контейнера внутри системы `taxi`. Все остальные представления ссылаются на этот контейнер по идентификатору `api`.

**Что произойдёт при переименовании:** в C4-PlantUML придётся править три файла вручную, и есть риск забыть один из них — тогда на Container и Component контейнер будет называться по-разному. В Structurizr DSL достаточно изменить одну строку в блоке `model`, и все три представления автоматически подхватят новое название. Это ключевое преимущество единой модели.

## 2. Что умеет C4-PlantUML, чего не умеет Structurizr DSL, и наоборот?

**C4-PlantUML умеет то, чего не умеет Structurizr DSL:**
- **Точный контроль над расположением элементов** через `skinparam`, `Lay_D`, `Lay_R`, `Lay_U`, `Lay_L`. Если нужно, чтобы конкретный контейнер был строго справа от другого, это задаётся явно.
- **Смешивание C4 с другими диаграммами PlantUML** в одном файле — например, вставить диаграмму развёртывания UML рядом с C4 Context или добавить заметки `note` к элементам.
- **Настройка внешнего вида** через `skinparam` — цвета, шрифты, границы, тени. Structurizr DSL использует готовые темы, и тонкая настройка сложнее.
- **Рендер стандартным PlantUML** — не требует отдельного CLI, работает в том же CI-шаге, что и остальные `.puml`.

**Structurizr DSL умеет то, чего не умеет C4-PlantUML:**
- **Единая модель** — описание один раз, генерация всех представлений из неё. Расхождения между уровнями исключены по построению.
- **Несколько представлений одного уровня** — например, отдельное Container-представление только для Backend API или только для платёжного контура. В C4-PlantUML для этого нужен отдельный `.puml`-файл.
- **Встроенная документация** — раздел `docs` в DSL позволяет привязать текстовые документы к элементам модели.
- **Экспорт в несколько форматов** — PlantUML, Mermaid, D2, PNG, SVG — одной командой CLI.
- **Проверка целостности модели** — Structurizr CLI проверяет, что все элементы, упомянутые в связях, существуют в модели.

## 3. Какой из четырёх уровней C4 оказался для вашей системы бесполезен и почему?

Для **службы такси** наименее полезным оказался **уровень 4 — Code**. Причины:

- Уровень Code — это диаграмма классов UML, которую мы уже сделали в ПР1, часть 3. C4 не добавляет к ней ничего нового.
- C4 прямо говорит: «четвёртый уровень редко нужен». Он дублирует то, что и так есть в коде и в диаграмме классов.
- В нашем случае доменная модель (`domain.puml`) уже описывает классы `Клиент`, `Водитель`, `Заказ`, `Поездка`, `Предложение`, `Тариф`, `Отзыв`, `Транзакция` — и повторять их на уровне C4 Code было бы избыточно.
- Практическая ценность уровня Code появляется только в очень крупных системах, где нужно показать внутреннее устройство конкретного компонента. У нас такой необходимости нет.

Поэтому мы ограничились тремя уровнями: Context, Container, Component. Это соответствует рекомендации Саймона Брауна: «рисуйте столько уровней, сколько нужно, и не больше».

## 4. Диаграмма компонентов UML и C4 Level 3 — в чём разница? Что бы вы выбрали?

**Диаграмма компонентов UML** показывает **физические и логические компоненты** системы: модули, библиотеки, исполняемые файлы, их интерфейсы и зависимости. Она ближе к реализации — на ней можно показать, что компонент `taxi-api.jar` зависит от `taxi-common.jar`. Аудитория — разработчики и DevOps.

**C4 Level 3 (Component)** показывает **логические компоненты внутри одного контейнера**: контроллеры, сервисы, репозитории, публикаторы событий. Она ближе к архитектуре — на ней видно, что `OrderService` использует `MatchService` и `PriceService`. Аудитория — команда этого контейнера и архитектор.

**Ключевая разница:**
- UML-компоненты — про **развёртывание и зависимости сборки**.
- C4-компоненты — про **ответственность и поток данных внутри контейнера**.

**Что бы я выбрал:** для нашей системы — **C4 Level 3**. Причины:
- У нас монолитное Backend API на Kotlin/Spring Boot, а не набор отдельных модулей. UML-компоненты показали бы один артефакт `taxi-api.jar`, что неинформативно.
- C4 Level 3 показывает логическое устройство: `OrderController` → `OrderService` → `MatchService` / `PriceService` / `OrderRepository`. Это полезно для нового разработчика.
- Компоненты C4 прослеживаются до классов ПР1 (`OrderService` → `Заказ`, `MatchService` → `Водитель` и `Предложение`), что обеспечивает согласованность модели.

UML-компоненты я бы использовал только если бы система была разбита на отдельные модули с чёткими интерфейсами между ними.

## 5. Диаграмма развёртывания UML не покрывается уровнями C4. Нужна ли она нашей системе?

**Да, нужна.** C4 Context/Container/Component показывают **логическое устройство** системы: какие контейнеры есть, как они связаны, какие технологии используют. Но они **не показывают физическое размещение**: на каких серверах, в каких кластерах, на каких портах.

Для службы такси физическое размещение важно, потому что:
- Backend API разворачивается в Kubernetes-кластере с несколькими подами (`api` ×3 для горизонтального масштабирования).
- Планировщик (`worker`) разворачивается в одном поде — он не требует масштабирования.
- PostgreSQL и RabbitMQ разворачиваются на отдельных серверах.
- Мобильное приложение и веб-панель диспетчера разворачиваются на устройствах пользователей.

Без диаграммы развёртывания невозможно ответить на вопросы: «Сколько подов API нам нужно?», «На каком порту слушает PostgreSQL?», «Какой протокол используется между API и очередью?». Поэтому мы рисуем `docs/06-c4/05-deployment.puml`.

Код диаграммы — в отдельном файле `05-deployment.puml`.

## Вывод

Разница между подходами принципиальна: C4-PlantUML — это **инструмент рисования**, Structurizr DSL — **инструмент моделирования**. Первый даёт полный контроль над картинкой, второй — над моделью. Для службы такси с восемью контейнерами и десятью компонентами единая модель Structurizr экономит время и исключает расхождения. Но полностью отказываться от C4-PlantUML не стоит: он остаётся незаменимым для динамических видов и диаграмм развёртывания, которые Structurizr DSL не покрывает.

Из четырёх уровней C4 для нашей системы оказался бесполезен уровень Code — он дублирует диаграмму классов UML из ПР1. Мы ограничились тремя уровнями: Context, Container, Component. Для уровня Component выбрали C4 Level 3, а не UML-компоненты, потому что у нас монолитное Backend API, и логическое устройство важнее зависимостей сборки. Диаграмму развёртывания UML добавили отдельно — она показывает физическое размещение, которое C4 не покрывает.
